# Deploy a full runtime release

Use this path when binaries, server contracts, observer, database or configuration
must change. The existing deployment owner runs one serialized attempt.

## Before starting

- Freeze exact reviewed receiving-main source/tree and all applicable successful
  PR and main checks. Do not transfer approval between heads.
- Bind actual authority, source qualification, configuration, process ownership
  and preserved assets. A null/unbound preparation field is not missing source
  qualification; adopt the existing authentic receipt where applicable.
- Verify the resource envelope for **each heavy job**, including actual kernel
  memory/CPU limits, finite wall time and cleanup. A controller cap does not cap
  a separate child scope.
- Use a fresh named attempt. Preserve failed directories, original proofs,
  retained output costs and rollback material. A consumed allocation requires a
  new actual owner disposition; no automatic extension or retry.
- Preflight every relative input, including authority.md and rendered scripts,
  before launching a build. Do not discover a missing preparation file after
  admission.

## Build, qualify and switch

1. Acquire both common deployment locks listed in UI_ONLY.md.
2. Recheck actual main, reviewed tree, current process identities, source and
   private configuration.
3. Build required runtime executables and the complete dashboard from the frozen
   source. Record exact binary and asset hashes.
4. Run the required Linux smoke checks against the **same binaries** being
   staged. A macOS result or a different Linux binary is separate evidence.
5. Verify the complete release manifest, including schemas, validators, lazy
   chunks and workers. Back up configuration and the authoritative database
   through their qualified backup procedure.
6. Start the replacement through the existing controller, verify health, auth
   boundaries, feeds, HTTP assets and process executable identities, then retire
   only the exact superseded owned processes.
7. Drive actual Chrome using VERIFY.md; save the screenshot and measured result.
8. Record rollback readiness and component versions, notify the existing owner
   route and perform only proven safe owned cleanup.

## Failure handling

Stop the affected attempt, retain evidence and determine whether production
changed. Report the actual exception and accountable next action.

The October 21 attempts separately failed on a missing preparation authority file
and an output-entry enumeration race. Neither was a GitHub permission problem or
a source CI failure. Do not weaken assertions or reset accounting to label a
failed attempt successful. If the change is actually UI-only, reassess whether
the simpler, compatible asset path is sufficient.

Private paths, credentials, databases, policies and service ownership do not
belong in a public release archive. Native/provider acceptance remains a separate
release criterion.
