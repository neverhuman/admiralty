# Durable asset custody and pins

`admiralty-store::custody` records immutable asset bindings, active pins, retirement claims and command receipts on a caller-owned SQLite connection. Every mutation uses one `IMMEDIATE` transaction for its compare-and-swap, observation checks, pin/claim interlock, receipt and projection validation. It never scans, changes or deletes an asset on disk. Receipts are output-only types with sealed `recorded_only: true` and `destructive_permission: false` fields. A recorded retirement claim grants no cleanup authority.

## Exact scope, clocks and policy

An immutable binding includes project, root, task, asset, owner, full lowercase `sha256:<64 hex>` content identity and a positive canonical decimal generation. Registration is insert-only with expected revision `0`. Asset IDs and pin IDs cannot be recycled, even after retirement or release. Later operations require the full original binding, generation and current revision. Counters are canonical decimal strings, including beyond JavaScript's precise integer range, and must fit SQLite's signed 64-bit range. Overflow fails before commit.

Each `CustodyObservation` now carries its own exact `binding`, `asset_revision` and `clock_id`, as well as `observed_at`, `decision_at`, `max_age`, provenance and explicit registered/foreign/dirty/held facts. Its binding must equal the request's full binding; its revision must equal the requested CAS revision. This prevents copying a clean observation from another asset, owner, content identity, generation, scope or revision. Missing facts, dirty/foreign/held facts, invalid clocks or stale evidence fail closed. These remain caller-recorded assertions: the module does not authenticate the observer, hash the actual asset, establish ownership or prove cleanliness.

Registration fixes the asset's clock domain and maximum observation age. Both remain immutable for that asset ID. Maximum age is positive and at most 86,400 caller-defined logical ticks; all timestamps and freshness calculations must use the same established clock domain. The module never reads wall time. Every new mutation requires `observed_at >= previous decision_at`, `decision_at >= observed_at`, and an age within the pinned policy. A new command/CAS cannot reset these retained floors; reopening the database preserves them. Unknown time must be reconciled by the caller, not filled with a guessed current clock.

Identifiers and provenance are opaque 1–128 byte ASCII references using letters, digits, underscores, periods, colons or hyphens; `.` and `..` are refused. They are not places for paths, credentials, logs or free-form instructions. Digest and counter representations have exact bounds. A shared streaming JSON admission check rejects typed requests above 1 MiB before serialization, hashing, cloning or database access. Retained receipt JSON is capped at 16 KiB in SQL before loading it into a Rust string.

## Durable receipt and projection consistency

Each successful mutation advances the asset revision and stores a full-binding receipt with command, operation, exact request digest, reference ID, source clock, timestamps, freshness policy and provenance. Reusing a command ID for a different valid operation/request is a collision. Exact replay returns the original historical receipt, including its original revision. It performs no projection update, pin reacquisition, clock reset or claim removal. A receipt describes its recorded revision; an old receipt does not describe the current asset state.

Before accepting new changes or returning a historical receipt, the module checks the current asset's complete bounded receipt closure. It reconstructs each typed request from the recorded validated facts, checks its digest and canonical receipt, verifies contiguous revisions, and replays pin acquisition/release and terminal retirement. This reconstructed state must equal the current asset clock/policy, timestamps, provenance, claim and exact pin rows. Missing pins, substituted bindings, changed receipt flags, forged receipt bytes, clock changes, projection rewind or inconsistent terminal state fail closed. This detects inconsistent stored data; it is not cryptographic authentication against an adversary able to rewrite the database and all its evidence consistently.

Prototype retention limits are 2,000 assets, 20,000 commands globally and 128 lifetime pin IDs per asset. Commands and released pins are retained; capacity exhaustion never prunes history, expires pins or frees custody. Each pin may be acquired once and released once, followed by at most one retirement claim, so per-asset verification reads at most 258 small receipts. A full pin history still permits releasing an existing pin. Global command exhaustion blocks new writes; exact historical replay remains possible when its closure is valid. Capacity policy changes require an explicit implementation/migration review.

## SQLite assumptions and concurrency

Pin acquisition and retirement serialize in the same write transaction. Active pins block retirement; a terminal claim blocks every subsequent fresh mutation. Release changes only an active pin with the full matching scope, owner, content digest and generation. Pins use a composite foreign key to that immutable asset binding. A denial rolls back without changing a pin, advancing a revision or appending a command receipt.

Call `initialize` explicitly on an autocommit connection. It enables foreign keys before opening its own transaction, creates the exact component-owned `STRICT` inline schema, and checks its foreign-key closure. It does not alter global `PRAGMA user_version` or another component's migrations. Older, partial or incompatible custody schemas are refused; old observations do not contain the new pins/clock policy, so the module never invents migration values or silently adopts them. Preserve a backup and design any migration explicitly before using such a database.

Every writer connection must enable foreign keys and configure a bounded SQLite busy timeout. Each mutation checks the exact custody table/index definitions and refuses unexpected triggers on the owned tables. Caller-owned nested transactions are refused. All module table references explicitly target `main`, so temporary shadow tables cannot redirect a custody write. These checks do not secure an untrusted SQLite connection, extension, VFS or hostile filesystem; connection/database custody remains the caller's responsibility.

The focused SQLite tests cover all six original scenarios plus cross-scope observation reuse, revision and clock/policy substitution, monotonic floors after reopen, historical replay after release/retirement without rewind, forged/oversized receipts, missing pins, corrupt projections, disabled foreign keys, nested transactions, legacy schemas, temporary table shadows, unexpected triggers, streaming admission and full lifetime pin history. Real separate connections exercise both sequential operation orderings and a simultaneous pin/retirement race; exactly one competing CAS commits.

This component is not automatically activated at startup and is not connected to filesystem cleanup, trusted inventory observation, provider execution or acceptance. Those integrations and their authority checks remain pending. A successful stored claim or receipt is evidence of a database mutation only.
