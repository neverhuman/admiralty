# Atomic event and effect-intent storage

`Store::append_with_intent` records a domain event, one canonical outbox intent, and their immutable association in a single SQLite `IMMEDIATE` transaction. The event reducer runs before commit; the in-memory projection and watch notification advance only after commit. A failed insert or association constraint rolls back both rows. The method returns a durable append receipt, not an effect execution or acceptance receipt.

The shared `admiralty_core::limits::bounded_json_size` checks escaped JSON bytes before allocating a serialized copy: 1 MiB for an event and 16 KiB for an outbox payload. Structural depth and node limits are checked before traversing a payload recursively; sorted object keys make its representation canonical. Keys are capped at 256 printable bytes, timestamps at 128 printable bytes, and `u64` sequence/deadline values are checked against SQLite's signed integer range. SQLite text is inspected as borrowed bounded bytes before copying it into owned strings.

The association snapshots the event sequence, unique outbox row, idempotency key, payload digest, deadline, and a digest of that intent identity. A separate immutable request binding records the producer, incarnation, source sequence, event hash, observation timestamp, and presence or identity of the effect. The event, intent, association, request binding, and producer watermark commit together. Foreign keys and immutable update/delete triggers prevent reassignment through ordinary SQL updates.

Exact replay requires the same source identity, serialized event and effect association. `observed_utc` is the receive observation: a retry may supply a fresh value, but the Store preserves the first-admission timestamp and its validated request binding. Such a retry returns a duplicate receipt without rewriting any event or intent, advancing the projection, or emitting a watch hint. An immutable clock inside the domain event remains part of event identity. A plain replay of an event that has an effect, an effect replay of a plain event, or any changed key, payload, or `not_before` schedule records an integrity incident and returns a source collision. An exact pre-existing outbox key cannot be attached to a second event, including when the original row was created through the legacy `outbox::enqueue` API. That collision is recorded and no second association is made. The public `Store::append` and `outbox::enqueue` APIs remain available with their prior responsibilities.

Migration `0003_atomic_effects.sql` is additive and idempotent. `Writer::open` explicitly applies it after foundation and outbox initialization. It intentionally leaves `PRAGMA user_version` at 1: that pragma remains under integration-owner control, and the current supported executable accepts versions through 1. A future coordinated global migration may advance it. Opening and rebuilding a store only initialize schema and replay domain events; they do not claim, deliver, or execute outbox work.

The migration runs in one transaction and records an immutable legacy event watermark. Events already present at upgrade retain their existing payload-hash validation; this cannot establish retroactive source provenance. Every event after that boundary requires its request binding. Startup, rebuild, duplicate append, and cursor reads verify canonical payloads, source metadata and request/effect bindings; missing or orphaned evidence fails closed. A direct database owner able to remove triggers and rewrite all evidence is outside this integrity mechanism: these unkeyed digests do not authenticate such an owner.

Tests use portable private temporary directories without a required Cargo target environment. They exercise real SQLite reopen, legacy upgrade, competing atomic appends, changed source/timestamp/effect evidence, and a forced request-binding insert failure that leaves no event, outbox row, association, watermark, projection change, or watch hint.

## Boundary

The outbox remains a durable proposal queue. This component does not launch providers, call a forge, perform network I/O, or establish publication authority. Claims, external execution, reconciliation, and acceptance are separate responsibilities.
